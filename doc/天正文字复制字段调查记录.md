# 天正文字复制字段调查记录

日期：2026-10-14

状态：回路标注 `Update` 刷新已排除，继续调查天正专用接口；天正多行目标写入仍停用

## 样本来源与字段

依据用户在真实 CAD 中运行 `TZTXTDBG` 提供的五个样本日志。本表中的句柄只属于该张测试图，不作为程序常量。

| 样本 | 对象类型与句柄 | 已确认的文字位置 |
| --- | --- | --- |
| 1，上方引线标注 | `TCH_MULTILEADER`，`1CA8` | `TDbSymbMultiLeader` 子类内的组码 `1` 为“排烟风机”，组码 `2` 为“11kW，吊装”；两段均需保留 |
| 2，导线标注 `wl1` | `TCH_WIREDIM2`，`1CAA` | 本体没有组码 `1`；XData `KeyOwnWireId` 的组码 `1005` 指向 `1CA9`；该 `LWPOLYLINE` 的 XData `linenum` 组码 `1000` 为 `wl1` |
| 3，数字标注 `3` | `ATTRIB`，`1CAC` | 组码 `1` 为 `3`，标签组码 `2` 为 `N`；它是属性文字 |
| 4，天正单行文字 | `TCH_TEXT`，`1CAE` | `TDbText` 子类内的组码 `1` 为“天正单行文字输入” |
| 5，天正多行文字 | `TCH_MTEXT`，`1CAF` | `TDbText` 子类内的组码 `1` 包含两行内容，行间为 CRLF；本样本还有 `TDbMText` 子类 |

第二份日志 `TZTXTDBG (1).txt` 已在本图确认 `TCH_WIREDIM2 -> KeyOwnWireId -> 导线 XData linenum` 的读取链。其 `TG_DIMWIRE_TYPE` 为 `WireNameOnly`，关联导线句柄为 `1CA9`。截图中容易把小写字母 `l` 看成数字 `1`；日志里的原值是 `wl1`。

COM 只读探测显示：`TCH_TEXT` (`TDbText`) 的 `Text` 属性可读、可写；`TCH_MULTILEADER`、`TCH_WIREDIM2`、`TCH_MTEXT` 在已探测的 `TextString`、`Text`、`Content`、`Contents`、`Text1`、`Text2`、`LineNum`、`WireName` 属性中都没有可用项。探测到 setter 仅说明接口存在，尚不能证明写入后能正确显示、保存重开及撤销。

## 当前代码与下一步

旧版 `maa` 对第二次点选的对象直接调用 `entmod`。现已加类型保护：普通 `TEXT`、`MTEXT`、`ATTRIB` 走原有写入路径；天正自定义目标不会进入 `entmod`。五类样本均可作为复制来源：引线标注根据 `nentsel` 拾取点相对组码 `11` 基线的位置与组码 `52` 方向，分别读取上方组码 `1` 或下方组码 `2`；导线标注只读关联导线的 `linenum`；属性文字、天正单行和多行文字读取组码 `1`。写入普通 `MTEXT` 时将 CRLF 转为 `\P`。`TCH_TEXT` 目标通过探测到的 COM `Text` 属性写入，并校验 COM 与 DXF 组码 `1` 的读回；校验不一致时尝试恢复原值。

`TCH_MULTILEADER` 目标根据拾取点选定 `UpText` 或 `DownText`，只写对应一行；写前核对其 COM 原值与相应 DXF 组码，写后核对该行新值及另一行原值。用户实测“引线标注 → `TCH_MTEXT`”时 CAD 崩溃闪退，因此已删除 `TCH_MTEXT` 候选 COM 属性写入分支：该类型仍可作为来源，作为目标时直接提示并返回，不调用 COM setter 或 `entmod`。目前没有足够证据判断是哪一个候选属性导致原生崩溃，不能将此前的可写标志视为安全证明。

`TCH_WIREDIM2` 目标此前因本体没有组码 `1` 而直接拒绝。随后仅对 `TG_DIMWIRE_TYPE = WireNameOnly`、单个 `KeyOwnWireId` 句柄指向标准 `LWPOLYLINE`、且其 `linenum` XData 恰有一个组码 `1000` 的结构尝试写入。代码通过 `entget` 只取得关联导线的 `linenum` 应用数据，再对这条标准导线调用 `entmod`，读回不一致时尝试恢复。它不对天正标注本体调用 `entmod`，也不把导线的其他 XData 应用交给此次修改。该字段属于导线，若同一条导线有其他关联标注，它们可能一起变化。

用户在真实 CAD 中复测发现：导线 `linenum` 已写入新值，之后把该标注作为复制来源时也读到新值，但原标注图面仍显示旧值。手动执行 `REGENALL` 后仍显示旧值。由此可确认，读回 `linenum` 与调用 `entupd`、`REGENALL` 均不足以证明 `TCH_WIREDIM2` 显示内容已同步；不能将该写入路径标记为功能验收通过。当前已暂停 `TCH_WIREDIM2` 目标写入，避免继续制造数据与图面不一致。其来源读取仍使用关联导线 `linenum`；遇到这类已失配标注，不应再把它作为复制来源。需要比较天正原生编辑前后的对象数据，并找到其更新关联标注的方式。

用户提供的 `TZWIREDIM-DIFF.txt` 记录了原生“编辑导线”前后同一标注 `1CAA` 与关联导线 `1CA9`：标注的 `entget` 数据和句柄未变；导线 `linenum` 从此前脚本写入的字符串变成 `123`，`lnoar` 从 `3x2.5` 变成 `2x2.5`，XData 应用顺序也改变。`lnoar` 的变化可能是用户在编辑窗口中同时修改了导线规格，不能推断它是显示刷新的必要条件。标注 COM 接口报告 `Update` 方法可用，而 `Regen`、`Refresh`、`Rebuild`、`Recalculate`、`SetText`、`SetWireName` 均不可用。原生编辑时标注没有可见的 DXF 字段变化，因此下一步单独验证 `vla-Update` 是否能在修改关联导线后使标注从新字段重建显示。

独立测试版 `MAATZTEST` 已在真实天正图中尝试修改 `linenum` 后调用标注 `vla-Update`。用户确认原生编辑可显示 `123`，但该测试后图面仍是旧值；命令行显示“刷新测试未通过，已恢复导线原值”。因此通用 `Update` 方法也不足以同步 `TCH_WIREDIM2`，不能将这条路径合入主命令。

用户提供的操作截图进一步确认：双击回路标注本身，会打开标题为“编辑导线标注”的天正窗口，其中有“编号”输入框。用户在此窗口把编号改为 `123` 后图面随之显示 `123`。这说明原生编辑确实能更新标注，尚不能确定其调用了哪一个天正私有接口。

在测试图副本中用 `APPLOAD` 加载 `test/TZWIREDIMCOM.lsp`；这个独立脚本会立即提示点选回路标注，不需要再次输入命令。然后从 AutoCAD 文本窗口（F2）复制 `TZWIREDIMCOM BEGIN` 至 `END` 之间的完整 COM 属性和方法清单。依据清单查找天正专用方法；若没有可调用的专用接口，继续调查双击打开的“编辑导线标注”窗口是否允许脚本传值。不要继续猜测并写入 `TCH_WIREDIM2` 自定义对象，也不要修改无关的 `lnoar` 导线规格。主命令 `maa` 继续拒绝这类目标；独立 `MAATZTEST` 的 `Update` 实验已证明在当前样本中无效。引线标注仍需分别测试上行和下行。以 `TCH_MTEXT` 为目标时应只显示“不支持此种操作”且不修改图纸。
